# Feature Specification: 查證閉環有效性

**Feature Branch**: `023-verification-efficacy`

**Created**: 2026-08-12

**Status**: Draft

**Input**: 2026-08-12 成本盤點的後續。決策層用連網查證逐條核對召回層線索，是分層設計（spec 022）的核心宣稱；但實測裁決成功率只有 22%，且失敗原因無法從產出反推。

## 背景與問題

晨報的外部事件走「召回層產線索 → 決策層逐條開啟原文核對 → 標記 confirmed / contradicted / unverifiable」。
這個閉環是憲章 I（召回與決策互為稽核）的落地方式，也是 spec 022 存在的理由。

**實測結果**：全部有 `fact_checks` 的報告合計 **9 則成功裁決 / 31 則 unverifiable（成功率 22%）**。

問題不只是成功率低，而是**低成功率的原因無法從產出區分**。`unverifiable` 這個判定同時涵蓋
三種完全不同的情況，讀報告的人（和調參的人）都無從分辨：

1. 開啟了原文，但原文確實沒有支持該敘述 ← 有價值的查證結果
2. 想開啟但**額度已用盡**，根本沒查 ← 偽裝成查證結果
3. 嘗試開啟但**連結打不開**（網域拒絕、逾時、失效） ← 偽裝成查證結果

目前只能靠人工閱讀 `note` 欄位的中文敘述去猜是哪一種。

### 現有證據與其侷限（必讀：這決定了本 spec 的做法）

| 日期 | 每篇查證次數上限 | 線索數 | 裁決成功 | 模型 note 顯示的原因 |
|---|---|---|---|---|
| 8/06 14:01 | 12 | 5 | **5/6 (83%)** | — |
| 8/07 ×2 | 5 | 7 | 0/14 | URL 全是搜尋引擎轉址（**已修**，非本 spec 範圍） |
| 8/10 | 3 | 8 | 0/6 | 「檢索工具額度**已**用盡」出現在第 1 則 |
| 8/11 | 3 | 8 | 0/6 | 「連結無法開啟」×6 |
| 8/12 | 3 | 8 | 4/8 | 2 個來源成功產出 4 則裁決後「額度用盡」 |

**兩個互相衝突的假說，現有資料無法分辨**：

- **假說 A（額度不足）**：每則線索分到的查證次數，8/06 是 2.4、8/10–12 是 0.375。
  8/10 與 8/12 的 note 都明寫撞到額度上限。
- **假說 B（來源打不開）**：8/11 完全沒提額度，6 則全是「連結無法開啟」。

**關鍵反證**：同一個新聞網域在上限 12 時查證成功、在上限 3 時失敗（全樣本 4 成功 / 5 失敗）。
所以**不能**把失敗歸因於「某些網域天生打不開」——至少不能只憑目前的資料這樣歸因。
（專案內既有一則註解主張「真正該修的是召回層的 URL 品質，不是多買幾次 fetch」，寫於 8/07，
當時的 0% 成功率實為轉址 bug 所致。該主張未經驗證，本 spec 不予採信。）

樣本數極小（6 篇報告、40 則裁決），且橫跨一次已修復的 bug。**任何調參都必須先有能分離
變因的資料**，否則只是換一組猜測。憲章 II 亦明訂：查證次數上限的調整 MUST 有遙測依據。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 分辨「沒查成」與「查不到」 (Priority: P1)

Jay 讀晨報時，能一眼分辨某則外部事件是「已核對原文但原文不支持」還是「系統根本沒能查證」。
維運時也能從累積資料回答「上週有幾成的查證失敗是額度不足造成的、幾成是來源打不開」。

**Why this priority**: 這是其他所有工作的前提。在能分離變因之前調整任何參數都是猜測，
而且憲章 II 禁止無遙測依據的調參。同時它自身就有價值——把「偽裝成查證結果」的 unverifiable
標示出來，直接改善報告的誠實度（憲章 III 的精神）。

**Independent Test**: 只做這一項就能驗收：跑一篇晨報，檢查每則未成功裁決的線索都帶有可機讀的
失敗原因分類；連續數日後可產出「失敗原因分布」統計。不需要動任何參數。

**Acceptance Scenarios**:

1. **Given** 某則線索的來源成功開啟但內容不支持該敘述，**When** 產出報告，**Then** 該則標記為
   「已核對」類別，且使用者看得出它是有效的查證結果。
2. **Given** 查證額度在處理某則線索前已用盡，**When** 產出報告，**Then** 該則標記為
   「未查證：額度不足」，且**不得**與「已核對但查不到」混為一談。
3. **Given** 某則線索的來源嘗試開啟後失敗，**When** 產出報告，**Then** 該則標記為
   「未查證：來源無法開啟」，並記錄可供統計的來源識別。
4. **Given** 累積 N 個交易日的報告，**When** 檢視彙總，**Then** 能得到各失敗原因的次數分布，
   足以判斷假說 A 與假說 B 何者為主因。

### User Story 2 - 未查證的內容不被當成已查證閱讀 (Priority: P1)

讀報告的人不會把「系統沒查成」的外部事件當成「經過查證的事實」採信。

**Why this priority**: 與 US1 同為 P1 但獨立可交付。目前的產出比不查證更糟——它看起來像查過了。
這是誠實性問題，不需要等資料收集完就該修，也不依賴任何參數調整。

**Independent Test**: 構造一篇「所有線索都未成功查證」的報告，確認使用者實際閱讀的介面
（報告內文、Discord、網頁）都明確標示該篇的外部事件未經查證。

**Acceptance Scenarios**:

1. **Given** 一篇報告中有外部事件未能實際核對原文，**When** 使用者閱讀任一輸出介面，
   **Then** 該事實明確可見，不需要展開 JSON 或翻 log。
2. **Given** 一篇報告的所有外部事件都未成功查證，**When** 使用者閱讀，**Then** 呈現效果
   等同於「本篇無經查證的外部事件」，而非「本篇有 8 則外部事件」。
3. **Given** 某則未經查證的線索，**When** 決策層引用它作為選股或方向判斷的依據，
   **Then** 該引用被擋下或明確降級標示（對齊憲章 III fail-closed）。

### User Story 3 - 依證據調整查證額度 (Priority: P2)

在 US1 的資料顯示額度確為主因時，調整每篇的查證次數配置，讓多數線索能被實際核對，
且單篇成本仍在預算內。

**Why this priority**: 依賴 US1 的資料才能執行，故排 P2。價值高（直接提升成功率）但**條件性**：
若資料顯示額度不是主因，本項應改為不執行而非硬做。

**Independent Test**: 在 US1 資料就緒後，以 A/B 或前後對照方式比較調整前後的裁決成功率與單篇成本。

**Acceptance Scenarios**:

1. **Given** US1 累積的資料顯示「額度不足」為失敗主因，**When** 調整查證額度配置，
   **Then** 裁決成功率相對於調整前顯著提升，且單篇成本增幅在預算容許範圍內。
2. **Given** 召回層某日產出的線索數高於平常，**When** 產生該篇晨報，**Then** 查證額度的配置
   能反映線索數量，不會出現「線索翻倍但額度不變」導致必然大量未查證。
3. **Given** 調整後單篇成本使月度投影超出上限，**When** 評估，**Then** 該調整不予採用，
   或搭配其他成本回收措施一併提出（憲章 II：新增成本必須說明如何回收）。

---

### User Story 4 - 提升召回層來源的可核對性 (Priority: P3)

召回層優先提供實際打得開的來源，減少查證額度浪費在必然失敗的連結上。

**Why this priority**: **條件性工作**——只有在 US1 的資料顯示特定來源系統性無法開啟時才執行。
排 P3 是因為現有反證顯示來源品質可能不是主因，貿然實作可能是解錯問題。

**Independent Test**: 在 US1 資料確認特定來源系統性失敗後，比較召回層調整前後的
「線索可核對比率」（成功開啟數 / 線索數）。

**Acceptance Scenarios**:

1. **Given** US1 資料顯示某些來源系統性無法開啟，**When** 召回層產生線索，
   **Then** 這些來源的出現頻率下降，且線索的整體可核對比率上升。
2. **Given** 召回層偏好可核對來源，**When** 某重大事件只有不可核對來源報導，
   **Then** 該事件仍會被提出（標示為無法核對），而非被靜默丟棄——覆蓋率不應為了成功率被犧牲。

---

### Edge Cases

- 召回層當日產出 0 則線索時，「查證成功率」的分母為 0——彙總統計不得因此當機或顯示為 0%。
- 一則線索的來源與另一則相同時（實測發生過：一個來源頁支撐 3 則裁決），額度計算與
  成功率統計不應重複計次。
- 決策層降級到備援供應商時完全不做查證——此情境的統計必須與「查證失敗」分開，
  否則會污染成功率基準。
- 節儉模式（預算降級）本就不掛查證工具，其 0 次查證是預期行為，不得計入失敗統計。
- 查證額度在同一則線索處理到一半時用盡——該則的狀態必須明確，不可留在未定義狀態。
- 同一來源在不同日期時而成功時而失敗（實測發生過）——來源分類必須容納「不穩定」而非
  二分為「可用 / 不可用」。

## Requirements *(mandatory)*

### Functional Requirements

**可觀測性（US1）**

- **FR-001**: 系統 MUST 對每一則召回層線索記錄其查證結局，且結局 MUST 可機讀分類為至少：
  已核對且支持、已核對但矛盾、已核對但原文不足、未查證（額度用盡）、未查證（來源無法開啟）。
- **FR-002**: 系統 MUST 區分「未查證」與「已核對但無法確認」，兩者不得共用同一個判定值。
- **FR-003**: 系統 MUST 記錄每則線索的來源識別（足以做網域層級彙總），以支援 US4 的判斷。
- **FR-004**: 系統 MUST 記錄每篇報告實際用掉的查證次數與當篇的額度上限，使「是否撞到上限」
  可由資料判定而非由自然語言推測。
- **FR-005**: 系統 MUST 提供跨報告的彙總方式，能回答「各失敗原因的分布」與「各來源的成功率」。
- **FR-006**: 查證結局的記錄 MUST 由系統從實際工具行為推導，MUST NOT 僅依賴模型自述——
  自述無法稽核，且模型有動機把未查證描述得像查過。

**誠實性（US2）**

- **FR-007**: 未經實際核對原文的外部事件，其未查證狀態 MUST 出現在使用者實際閱讀的所有輸出
  介面上（報告內文、通知、網頁），MUST NOT 僅存在於結構化資料或日誌中。
- **FR-008**: 當一篇報告的外部事件全數未經查證時，系統 MUST 以等同「本篇無經查證外部事件」
  的方式呈現，避免讀者誤認為該篇有外部事實基礎。
- **FR-009**: 未經查證的線索 MUST NOT 被當作已查證事實引用於選股理由或方向判斷；
  若模型如此引用，系統 MUST 擋下或明確降級標示（對齊憲章 III）。

**額度配置（US3，條件性）**

- **FR-010**: 查證額度的任何調整 MUST 以 FR-001~FR-005 累積的資料為依據，並在變更紀錄中
  引用該資料（憲章 II）。
- **FR-011**: 額度配置 MUST 能反映當篇線索數量，避免線索數變動時額度與需求脫節。
- **FR-012**: 額度調整後的單篇成本 MUST 使月度投影維持在預算上限內；若否，該調整
  MUST 附帶成本回收方案或不予採用。

**召回層來源（US4，條件性）**

- **FR-013**: 若資料顯示特定來源系統性無法核對，召回層 MUST 降低其優先序；
  但 MUST NOT 因此丟棄該來源獨有的重大事件——覆蓋率不得為成功率犧牲。

### Key Entities

- **線索（Clue）**：召回層產出的一則待查證陳述，含敘述、日期、來源名稱、來源連結。
- **查證結局（Verification Outcome）**：一則線索的查證結果，含結局分類、失敗原因（如適用）、
  來源識別、是否實際開啟過原文。
- **查證額度使用（Verification Budget Usage）**：單篇報告層級的查證次數上限、實際使用次數、
  是否耗盡。
- **來源可核對性紀錄（Source Reachability Record）**：跨報告彙總的來源層級統計，
  含成功次數、失敗次數、失敗原因分布。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 針對任一篇報告的任一則外部事件，維運者能在 1 分鐘內判定它屬於「已核對」
  或「未查證」，且不需閱讀自然語言敘述或翻閱日誌。
- **SC-002**: 累積 10 個交易日後，能以數據回答「查證失敗中有幾成源於額度不足、幾成源於
  來源無法開啟」，且兩者相加涵蓋 95% 以上的失敗案例（其餘歸為其他原因）。
- **SC-003**: 讀者在任一輸出介面上，都能在不展開結構化資料的情況下得知該篇外部事件
  是否經過查證。
- **SC-004**: 未經查證的外部事件被當作已查證事實引用於選股理由的情況為 0。
- **SC-005**（US3 執行後）：裁決成功率由現行 22% 提升至 50% 以上，且單篇成本的月度投影
  維持在預算上限內。
- **SC-006**（US3 執行後）：「因額度不足而未查證」的線索占比低於 10%。
- **SC-007**: 上述任何調整都不得降低召回層的事件覆蓋率——每篇的線索數不低於調整前的水準。

## Assumptions

- 「裁決成功」定義為判定結果為 confirmed 或 contradicted（兩者都代表實際核對過原文），
  unverifiable 視為未成功。此定義沿用盤點時的口徑，便於前後對照。
- 轉址解析問題（8/07 的 0% 成功率主因）已修復，不在本 spec 範圍；但歷史資料做統計時
  MUST 排除該期間，否則會污染基準。
- 現行每篇查證次數上限為固定值 3，召回層每篇產出 5–10 則線索——此配置在數學上即保證
  多數線索無法核對，故 US3 的前提「額度可能不足」有表面合理性，但仍需資料佐證。
- 連網查證工具不按次計費，成本來自每輪重送的對話前綴；已啟用前綴快取，重讀成本為原價的一成。
  因此提高查證次數的邊際成本遠低於快取啟用前的實測值——舊的成本估計不可直接沿用。
- 現行月度預算與單篇成本水準只容許每日產生一篇晨報，額度調整的成本空間有限。
- 決策層降級路徑（備援供應商）不做查證，其產出不納入查證成功率統計。
- 樣本規模小（6 篇報告、40 則裁決）且橫跨一次已修復的缺陷，因此本 spec 刻意將
  「收集可分離變因的資料」列為 P1，而非直接進行參數調整。
